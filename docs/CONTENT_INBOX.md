# Content Inbox and Curated Ingestion

Status: design for issue #39

## Purpose

Argus needs a low-friction way to capture subjects the user wants to learn without weakening the product rule that a real Argus topic must have a finite, explicit completion boundary.

The solution is a small **content inbox** that sits outside the learning library.

A content-inbox request records intent such as:

- `Maritime signal flags`
- `Cloud types and what they indicate`
- `https://example.com/article — useful section on knots`

It is deliberately allowed to be incomplete, broad, ambiguous or merely a URL. It has no learning status and proves nothing.

A later ingestion run converts suitable requests into researched, bounded Argus content through the normal repository and pull-request workflow.

The governing flow is:

```text
notice something worth learning
        ↓
+ / Want to learn
        ↓
content inbox
        ↓
periodic ingestion
        ↓
research + finite-boundary design
        ↓
normal Argus content changes
        ↓
reviewed pull request
        ↓
shipped catalog topic
```

## Core product distinction

The inbox and the learning library are different systems with different standards.

### Content inbox

A request means only:

> I may want Argus to teach me something about this.

It may contain plain text, a URL, or a URL plus a short note. It may eventually be rejected, split into several topics, merged with an existing topic, deferred, or researched into a new topic.

A request has no `scope`, no scored `items`, no Learn/Test mode, no scheduler state, no completion state, no retention evidence and no learner claim.

### Argus topic

A topic remains a finite learning contract. Before it can enter the shipped catalog it must have an explicit scope/completion claim and scored material that completely covers that claim. Rich Learn support may explain that boundary but may not silently broaden it.

**A pending inbox request must never be represented as an unstarted Topic.**

This separation is the main architectural decision in this feature.

## V1 decisions

The following decisions are settled for the first implementation.

1. **Cloud Firestore stores only the content inbox.** It does not become the Argus library or learner-state database.
2. The existing local-first library, migration and JSON export/import model remains authoritative for learning state.
3. Argus remains a statically hosted client. No application server or new hosting tier is required for capture.
4. The static client uses the Firebase web SDK to access Firestore directly.
5. Firebase Authentication is required. V1 uses Google sign-in and Firestore Security Rules allow access only to the sole authorized Firebase UID.
6. Firestore generates request document IDs. These IDs are queue identity only and never become Argus topic or item IDs.
7. Capture uses one primary text field. The value may be a subject, URL, or URL plus note.
8. Track is optional at capture time and defaults to `Auto`. If supplied it maps only to the existing `learning`, `survival` or `tradecraft` tracks.
9. Pending requests appear in Library in a compact **Want to learn** section, separate from real topics.
10. Ingestion produces ordinary repository changes and a reviewable pull request. Generated curriculum is never auto-published.
11. A request becomes `added` only after its resulting topic or topics have actually shipped.
12. New shipped catalog topics require a general safe catalog-reconciliation mechanism so existing local libraries can receive them without losing learner state.

## Why Firestore is narrow

The problem that needs cloud state is small: capture an idea on one device and make it available to a later maintainer/agent ingestion run.

Moving the whole Argus library into Firestore would introduce unrelated complexity:

- cross-device learner-state synchronization;
- conflict resolution;
- remote availability becoming relevant to Learn/Test;
- cloud migration semantics for attempts and cue evidence;
- additional failure modes for a product that is currently local-first and portable through export/import.

None of that is required to solve capture.

The intended split is therefore:

| Data | Authority |
| --- | --- |
| learning topics on the device | existing local Argus library |
| scheduler / history / cue evidence | existing local Argus library |
| export/import | existing JSON format |
| vague future-content requests | Firestore content inbox |
| reviewed shipped curriculum | Git repository / shipped catalog |

## Identity model

There are three independent identities.

### Inbox request ID

Generated by Firestore.

Purpose: uniquely address a request record and support deletion/status updates.

This ID has no curriculum meaning.

### Topic ID

Stable Argus curriculum identity such as `nato-phonetic` or `international-morse-letters-printed`.

Purpose: reconcile topics, preserve learner history and reason about deliberate content migrations.

Topic IDs must remain deliberately authored. The ingestion process must not copy a Firestore auto-ID into `Topic.id`.

### Item ID

Stable Argus scored-item identity.

Purpose: preserve per-item evidence through editing/reordering and support item-specific learning state.

Inbox work must not redefine existing item-identity semantics.

## Remote data model

The Firestore boundary should remain small and explicit.

Conceptually:

```ts
type TrackHint = 'learning' | 'survival' | 'tradecraft'

type ContentRequest = {
  text: string
  status: 'pending' | 'added'
  trackHint?: TrackHint | null
  createdAt: Timestamp
  topicIds?: string[]
  addedAt?: Timestamp
}
```

Collection shape:

```text
users/{authorizedUid}/inbox/{autoId}
```

### Required invariants

For `pending` requests:

- `text` is non-empty after trimming;
- `createdAt` is server-controlled or server-timestamp based;
- `topicIds` and `addedAt` are absent;
- `trackHint`, if present, is one of the existing Argus tracks.

For `added` requests:

- original `text`, `createdAt` and any `trackHint` remain intact;
- `topicIds` contains at least one shipped Argus topic ID;
- `addedAt` is present.

V1 does not need a large workflow-status vocabulary. Research/review state belongs in GitHub once ingestion begins. If operational experience later proves that `rejected` or `deferred` is valuable, add it deliberately rather than pre-building a workflow engine.

## Authentication and security

The app is single-user, but the public web client must not have an open write path.

V1 uses Firebase Authentication with Google sign-in. Firestore Security Rules must restrict reads and writes to the sole authorized Firebase UID.

Conceptually:

```text
allow read, write: if request.auth != null
                   && request.auth.uid == AUTHORIZED_UID;
```

The exact UID is configuration/identity, not a privileged credential. No service-account key, GitHub token, Firebase Admin credential or other secret may be shipped in the browser bundle.

Rules should also constrain the permitted document shape and status transitions where practical. Client validation is for usability; Security Rules remain the trust boundary for browser writes.

The maintainer/agent ingestion path may use privileged credentials outside the PWA, for example from a local environment or appropriately configured CI. Those credentials are not part of the client architecture.

## Capture UX

The capture surface should optimize for the moment an idea occurs, not for curriculum authoring.

### Entry point

Use a prominent but calm `+` action associated with Library.

The current `New topic` action remains available for direct manual topic authoring. The inbox `+` should not silently replace that capability.

### Interaction

Expected V1 flow:

1. user taps `+`;
2. a compact mobile sheet/dialog opens;
3. prompt: **What do you want to learn?**;
4. one text field receives an idea, URL, or URL + note;
5. optional track control defaults to **Auto**;
6. user taps **Add**;
7. the request appears in **Want to learn**.

The capture flow must not ask for:

- topic title as a distinct field;
- scope/completion claim;
- scored prompt/answer pairs;
- Learn sections;
- sources;
- case studies;
- difficulty or scheduler metadata.

Those are ingestion/editorial decisions.

### Library presentation

Pending requests appear in a small section such as:

```text
Want to learn · 3

Maritime signal flags
Cloud types and what they indicate
Knots used in sailing
```

This section must not use the same status/shelf language as unstarted, learning, drilled, completed or decayed Topics.

A request row may be removed before ingestion. V1 does not need a full edit screen; reopening the capture text for a small edit is acceptable if inexpensive, but delete + recapture is sufficient.

Added requests do not need to remain prominent in the main Library. They may disappear from the pending queue once the resulting topic exists. The durable Firestore record remains useful for ingestion provenance/history.

## First-use and failure behavior

### Authentication

If capture is used before authentication is configured, present a small first-use sign-in path. Authentication should feel like setup for the cloud inbox, not like Argus becoming an account-centric product.

Learn/Test and the local library must remain usable when the inbox is signed out or unavailable.

### Network failure

Capture must not silently discard typed text.

At minimum:

- keep the field contents intact when a remote write fails;
- show a clear retryable error;
- never close the sheet and imply success until the request is safely queued/acknowledged by the chosen client persistence model.

If implementation enables Firestore persistent local caching, the UX may distinguish **queued on this device** from **synced**, but V1 must not claim remote success merely because a local optimistic write exists.

Do not make general Argus functionality dependent on Firestore connectivity.

## Ingestion contract

Ingestion is a maintainer/editorial workflow, not a runtime learning mode.

A maintainer or agent should be able to run a documented command/workflow that reads pending requests and prepares content work.

For each request it must treat the captured text as **intent**, not source material or a curriculum specification.

The ingestion process should:

1. read pending requests;
2. identify duplicates/overlap with shipped topics and other pending requests;
3. research the subject using appropriate authoritative or primary-quality sources;
4. decide whether the request can produce a finite Argus topic;
5. split broad requests when one honest completion boundary would be too vague;
6. define the exact completion claim before authoring scored items;
7. choose the appropriate Learn treatment: reference-only, concise support, or briefing;
8. create scored material that completely covers the stated boundary;
9. preserve provenance and safety/limitations requirements;
10. assign deliberate stable topic/item identities;
11. run the normal validation suite;
12. open a normal branch/pull request for review.

Several compatible requests may be batched into one ingestion PR when that improves efficiency without making review ambiguous.

### No automatic curriculum publication

The ingestion system must not:

- write generated topics directly into production;
- automatically merge content PRs;
- treat an LLM-generated answer as sufficient factual provenance;
- mark a request `added` because a draft was generated;
- create vague completion claims merely to fit a request into one topic.

Git remains the durable review boundary for shipped curriculum.

### Marking a request added

A request changes from `pending` to `added` only after the resulting topic or topics are actually merged/shipped.

The update records:

```text
status: added
topicIds: [stable shipped topic ids]
addedAt: server timestamp
```

This may be performed by a post-merge maintainer command or an explicitly designed CI step. The implementation should prefer a mechanism that is idempotent and cannot mark an unmerged draft as shipped.

## Catalog reconciliation

This feature exposes an existing architectural gap: adding a new topic to the repository seed/catalog does not by itself guarantee that a browser with an existing local library will receive that topic.

V1 therefore requires a general shipped-catalog reconciliation policy.

### Desired behavior

When Argus starts with an existing valid local library:

- identify shipped catalog topics missing from that library;
- add eligible missing catalog topics as fresh `unstarted` topics;
- preserve every existing learner-owned durable field for topics already present.

### Collision rule

A matching `topic.id` is not sufficient permission to overwrite local data.

Reconciliation must distinguish at least:

- known shipped topic already present locally;
- genuinely missing shipped topic;
- user-authored/local topic that happens to collide with a shipped ID;
- shipped topic whose semantic completion boundary has intentionally changed and therefore requires an explicit migration.

A user-authored collision must never be silently replaced.

Implementation may need durable provenance/ownership metadata or another deterministic mechanism to distinguish shipped catalog records from local authoring. That design belongs to #39 and must be tested before broad catalog merging is enabled.

### Existing-topic changes

General reconciliation is for **delivery of missing catalog content**, not blanket replacement of current topics.

If the shipped definition of an existing topic changes in a way that affects scored material, item identity, completion semantics or Learn content that must be refreshed, handle it through an explicit migration/reconciliation rule appropriate to that change.

Do not turn the special Morse absorption logic into a generic "repository wins" overwrite policy.

### Preservation invariants

Catalog reconciliation must not accidentally change or erase:

- status;
- creation/learning/drilling/completion timestamps;
- last-tested/spot-check timestamps;
- attempt history;
- per-item evidence;
- stable item IDs;
- user-authored topics;
- valid export/import behavior.

## Relationship to manual `New topic`

The existing full topic-authoring form still has value for cases where the user already knows the finite boundary and wants to author material directly.

The inbox solves a different problem: **capture now, design later**.

These should coexist:

- `+` / Want to learn → cheap content request;
- `New topic` → deliberate direct authoring.

If later usage shows direct authoring is unnecessary, that can be a separate product decision. Do not remove or weaken it incidentally in #39.

## Operational lifecycle

A normal cycle should be:

1. capture ideas casually over days/weeks;
2. run ingestion when desired;
3. agent/maintainer groups and researches pending entries;
4. review proposed finite boundaries and content in Git;
5. merge only green, acceptable curriculum;
6. deploy normally;
7. catalog reconciliation exposes new topics to the existing local library;
8. mark corresponding inbox entries `added`.

This keeps cloud state tiny while making content growth continuous.

## Non-goals

V1 explicitly does not include:

- multi-user account architecture;
- cloud sync of learner progress;
- shared or collaborative inboxes/libraries;
- a general content-management system;
- attachments or file uploads;
- rich-text editing;
- AI generation in the capture sheet;
- automatic curriculum merging/deployment;
- arbitrary remote modification of an existing learner topic;
- replacement of JSON export/import;
- a new learning mode;
- changes to existing scheduler/completion semantics.

## Implementation sequence

The work may be executed in one issue but should be developed in separable pieces.

### A. Inbox foundation

- Firebase client configuration;
- Google authentication;
- Firestore collection and Security Rules;
- typed inbox client/repository boundary;
- security/emulator or equivalent rules tests.

### B. Capture and Library UI

- `+` capture action;
- compact sheet/dialog;
- Auto/track hint;
- Want to learn list;
- delete pending request;
- first-use, loading and failure states;
- mobile/accessibility validation.

### C. Ingestion workflow

- documented maintainer command/tooling to read pending requests;
- clear output/hand-off into normal research/content PR work;
- safe post-ship status update.

### D. Catalog reconciliation

- deterministic distinction between shipped and local/user-authored content;
- add missing shipped topics without replacing existing state;
- explicit collision behavior;
- regression tests for migration/export/import/evidence preservation.

The implementation agent may split these into child issues/PRs if doing so materially improves review or isolates risk. #39 remains the product/architecture authority.

## Acceptance principles

The feature is correct when all of the following are simultaneously true:

- capturing a future learning idea takes only a few seconds;
- a vague request cannot masquerade as a learnable/completable topic;
- Firestore compromise/failure cannot corrupt the local learning library;
- unauthorized browser clients cannot use the inbox;
- no privileged credential is shipped to the client;
- ingestion remains evidence-led and review-gated;
- request identity is separate from curriculum identity;
- new shipped topics reach an existing learner safely;
- existing learner state survives catalog growth;
- Argus remains Learn + Test, local-first, finite-boundary and exportable.
